# Assumptions Log — Phase 1 (Foundation)

Every place the master spec left a decision open, here's what was assumed and why. Extend this file as later phases add their own assumptions — don't start a new file per phase.

## Identity & Auth

- **OTP-only auth, no passwords.** Matches standard consumer food-delivery UX (Swiggy/Zomato-style). Restaurant owners and delivery partners also onboard via OTP; admin users are the one role that may eventually need password + 2FA (Phase 9 hardening), since they're not doing OTP-friendly mobile onboarding.
- **Signup and login share one endpoint (`/auth/otp/verify`).** If the identifier doesn't exist, a new user is created inline rather than forcing a separate signup call. Reduces client-side branching; the `is_new_user` flag in the response lets the client show a "complete your profile" screen when needed.
- **Refresh token rotation with reuse detection.** Every refresh call issues a new refresh token and revokes the old one. If a revoked token is presented again, the entire token family is revoked — this is the standard mitigation for stolen refresh tokens and was not explicitly requested but is required for "token rotation" + "secure-by-default" from the spec.
- **Access tokens are stateless JWT (HS256), never persisted.** Only refresh tokens are stored (hashed, SHA-256) so they can be individually revoked. HS256 chosen over RS256 for Phase 1 since there's a single backend service verifying its own tokens; move to RS256/JWKS only if a separate service ever needs to verify tokens independently (documented as a Phase 8+ migration trigger, not a Phase 1 need).
- **OTP identifiers are phone OR email**, disambiguated by presence of `@`. International phone numbers are expected in E.164 format (`+91...`); no phone-format validation library wired yet — flagged as a TODO for Phase 1 hardening.
- **OTP rate limiting is two-layered**: a per-IP Redis fixed-window limiter (global middleware) plus a per-identifier daily cap + resend cooldown (application-layer, backed by Postgres `otp_challenges` history). This covers both "one attacker hitting many identifiers" and "one identifier being spammed from many IPs."

## Database access

- **sqlc over GORM**, as instructed to choose one. Rationale: sqlc generates compile-time-checked Go from hand-written SQL, so query correctness is caught at build time and there's no ORM-generated N+1 risk once order/pricing/settlement queries get complex (multi-table joins across orders → order_items → menu_items → restaurants are common in this domain). The tradeoff is more boilerplate per query — acceptable given the platform's long lifetime.
- **pgx/v5 as the driver** (not database/sql + lib/pq) — sqlc's `pgx/v5` mode gives native support for Postgres-specific types (UUID, inet, arrays) without extra marshaling code.

## Config & secrets

- Local dev defaults are baked into `config.go` (`setDefaults`) so a fresh clone runs with zero required env vars. Config validation hard-fails on missing JWT/DB secrets for any non-`local` environment — this is intentional so a misconfigured staging/prod deploy fails at startup, not silently with a dev secret in production.

## Modules NOT yet implemented (explicitly out of scope for this delivery)

Everything outside Identity/Auth and Users — Restaurants, Menu, Cart, Orders, Payments, Delivery, Settlements, Notifications, Admin RBAC, Search, etc. — per the Phase 1→9 roadmap in the master spec. Build order should continue to follow that roadmap (Phase 2: Restaurants + Menu next).

## Open items / TODOs surfaced in code

- `internal/modules/identity/infrastructure/repository.go`: `toInet` uses `net/netip` for IP parsing — verify behavior against IPv6 client IPs from real load balancers (e.g. X-Forwarded-For chains) before relying on it for fraud/abuse signals.
- OTP/SMS/Email providers are mocked (`MockOTPSender` logs the code). Real MSG91/Twilio + SES/SendGrid integrations are deferred to Phase 6 (Notifications) per the roadmap, but the `domain.OTPSender` interface is already in place so wiring them in later doesn't touch application logic.
- **No automated tests yet** for Phase 1 — Phase 9 in the roadmap is "Testing / Security hardening / Observability / Deployment," but unit tests for `AuthService` (OTP validation, token rotation/reuse detection) should realistically be written alongside the code, not deferred that far. Flagging as a risk, not following the roadmap blindly here.

## Phase 2 — Restaurants & Menu

- **Restaurants module scope**: covers Restaurants (core profile), Restaurant Owners (implicit — `owner_user_id` FK to `users`, role enforced via existing `restaurant_owner` role), Restaurant Staff (delegated accounts with an enum permission array — simpler than a full RBAC join table since staff permissions are restaurant-scoped, not platform-wide; platform-wide RBAC is a separate later module per the roadmap), Restaurant Documents/KYC, Operating Hours, and Service Areas.
- **Service areas are radius-based (a single `radius_km` per restaurant), not polygon-based.** The master spec's wider "Delivery Zones" concept (admin-defined polygonal zones covering a whole city) is a platform-level module for Phase 5 (Delivery); a restaurant's *own* service radius is a simpler, independent concept and doesn't need to wait for that. If polygon-level per-restaurant zones are wanted instead, `restaurant_service_areas` would need a `GEOGRAPHY(Polygon)` column and the nearby-search query would swap `ST_DWithin` for `ST_Contains` — flagged as a straightforward but non-trivial follow-up, not done here to avoid over-building ahead of the actual requirement.
- **Restaurant approval workflow**: `draft` → `pending_approval` → `approved`/`rejected`, gated by `SubmitForApproval` requiring operating hours to be set and the three legally-required documents (FSSAI license, GST certificate, PAN card) to at least be uploaded. Bank account proof and owner identity proof are supported document types but not blocking for submission — assumed optional for MVP approval, required later for payout setup (Payments module). Revisit if that assumption is wrong.
- **`is_accepting_orders` is separate from `status = approved`.** A restaurant can be approved but toggle itself closed (owner going on a break, temporarily out of stock, etc.) without losing its approval status or having to re-submit for KYC review. `SetAcceptingOrders(true)` is blocked unless the restaurant is already approved.
- **Nearby-restaurant search enforces each restaurant's own service radius**, not just the customer's search radius — a restaurant 8km away with a 5km delivery radius won't appear even inside a 10km customer search. This was an inference from how food delivery apps actually behave, not explicitly specified — worth confirming against the wireframes doc if one exists.
- **PostGIS `geography(Point)` column for restaurant location** is written via `ST_MakePoint(lng, lat)` inline in the `CreateRestaurant` query rather than passed as a bound parameter, and is *not* decoded back out of `SELECT *` results in Go (the field is mapped in `sqlc.yaml` to a raw `[]byte` override and simply dropped in `mapRestaurant`). This is because pgx doesn't have a built-in `geography` codec without extra type registration. If restaurant detail pages need to show/edit the raw lat/lng later, add a dedicated query using `ST_X(location::geometry)`/`ST_Y(location::geometry)` rather than trying to decode the geography type generically — flagged as a Phase 2 follow-up, not blocking for now since search already returns `distance_km`.
- **Menu pricing model**: `menu_items.base_price` is used directly when an item has no variant groups. When variant groups exist, the client is expected to require a variant selection and the selected variant's `price` REPLACES (not adds to) the base price; add-ons always ADD on top of whichever price was selected. This mirrors Swiggy/Zomato-style "Half/Full" (variant) vs "Extra cheese" (add-on) UX. Cart-time enforcement of "variant required if groups exist" is deferred to the Cart module (Phase 3) — this module only stores the data and shape.
- **`GetFullMenu` does N+1 queries per item** (variant groups, then variants per group; addon groups, then addons per group) rather than one large join, to keep individual queries simple and match how sqlc structures one query per return-shape. This will need a caching layer (Redis, cache-aside, invalidated on any menu write) before it's fast enough for high-traffic restaurant pages — flagged as a near-term perf follow-up, not done in Phase 2 to avoid premature optimization on unmeasured code.
- **Menu category/item soft-delete asymmetry**: `menu_items` has `deleted_at` (soft delete, matches `users`/`restaurants` convention) but `menu_categories` uses a hard `DELETE`. Assumption: categories are cheap to recreate and rarely need an audit trail, while items may have historical order references later (Phase 4) that would break with a hard delete. Revisit if categories ever need referential history too.

## Phase 3 — Cart & Orders

- **One active cart per customer, not per (customer, restaurant) pair.** `carts.customer_id` is UNIQUE. Adding an item from a different restaurant than the customer's current cart silently clears the old cart and starts a new one for the new restaurant — matches standard food-delivery-app UX (Swiggy/Zomato both do this) and avoids the added complexity of a multi-cart UI that hasn't been asked for.
- **Cart pricing is always computed live** (`ListPricedItems` joins against current `menu_items`/`menu_item_variants`/`menu_addons`) — a cart is not itself an immutable record, so if the restaurant changes a price while an item sits in someone's cart, the cart reflects the new price. This is intentional and is exactly why Orders (Phase 3's other module) exists as a separate, snapshotted record: the order is the actual price commitment, the cart is just a live shopping list.
- **Checkout requires the whole cart to be available.** If any item, selected variant, or selected add-on has gone unavailable since being added, `HasUnavailable` blocks checkout with a conflict error rather than silently dropping the unavailable item and charging for a partial order — the customer app is expected to show which item(s) need attention. Auto-dropping unavailable items was considered and rejected: it can silently change what the customer thought they were ordering.
- **`OrderService.Checkout` composes across three modules** (Cart, Restaurants, Orders) via two small interfaces (`CartReader`, `RestaurantReader`) rather than importing the full application services — keeps the dependency surface honest and swappable for tests. This is the first cross-module orchestration in the codebase; the same pattern (small consumer-defined interface, not a shared "god" service) should be reused for Phase 4+ modules that also need to read across boundaries (e.g. Delivery needs to read Orders).
- **Order creation is NOT wrapped in `db.WithTx` yet.** `Repository.Create` does header insert → N item inserts → per-item addon inserts as separate statements. A failure partway through leaves a partial order row. This is flagged as a real gap, not a deliberate simplification — the fix is straightforward (thread a `pgx.Tx` through the repository, wrap the whole `Create` call from `main.go`'s composition or via a `db.Postgres.WithTx` callback) but wasn't done in this pass to avoid changing the `Repository` constructor signature for every module in the same commit. Prioritize this before any real traffic hits checkout.
- **Order number format**: 6-character random alphanumeric (excluding ambiguous `0/O/1/I`), prefixed `FD-` (e.g. `FD-8K3N2Q`). No collision-retry loop exists yet — at low order volume the odds are negligible, but this needs a unique-constraint-violation retry loop before scale (the `order_number` column is already `UNIQUE`, so collisions fail loudly rather than corrupting data — they just aren't retried automatically yet).
- **Pricing model for Phase 3 is deliberately simple**: flat 5% tax rate and flat ₹40 delivery fee, both hardcoded in `main.go`'s `PricingConfig`, no per-restaurant tax override, no distance-based or surge delivery pricing, no promotions/discounts (that module doesn't exist yet — `discount_amount` is always 0). This is very likely wrong for a real launch and is the single biggest "come back and fix this" item from Phase 3 — flagging clearly rather than pretending it's production-ready.
- **Order status state machine is linear with one branch**: `placed → confirmed → preparing → ready_for_pickup → out_for_delivery → delivered`, with `cancelled` reachable from `placed`/`confirmed`/`preparing` only (not after food is ready, on the assumption that cancelling ready-or-later orders should go through a support/refund flow rather than a simple status flip — no such flow exists yet, so in practice a `ready_for_pickup` order currently cannot be cancelled through the API at all). Flag this to the person if "restaurant marks ready then customer wants to cancel" turns out to be a real flow that needs handling before Delivery (Phase 5) is built.
- **Order read/write access control**: `GetByID`, `GetStatusHistory`, and `Cancel` all check that the requesting user is either the order's own customer or an admin (`OrderHandler.canAccessOrder`) before returning data — this closes an ownership gap that existed in an earlier draft of this module. `TrackByNumber` (`GET /orders/track/:orderNumber`) is deliberately NOT ownership-checked beyond requiring authentication: an order number is treated like a receipt/tracking code (shared via SMS/email confirmation), not a secret tied to account identity, matching how most delivery platforms let you track a package with just the tracking number. Revisit if that assumption doesn't match the intended UX. Restaurant-side routes (`/restaurants/:id/orders/*`) rely on the existing `ownerOnly` role gate but do not yet verify the requesting owner/staff belongs to *that specific* restaurant — same class of gap as the original customer-order issue, not yet fixed, flagged here for Phase 4 cleanup.

## Phase 4 — Payments

- **Gateway abstracted behind `domain.PaymentGateway`, shipped with only a mock implementation.** `CreateOrder`, `VerifyCallback`, `Refund` are the three operations every mainstream gateway (Razorpay, Stripe, PayU, Cashfree) maps onto reasonably well, so this interface shape should hold when a real gateway is wired in — but it hasn't been validated against any specific provider's actual SDK/API shape yet. Treat it as a reasonable starting contract, not a guarantee it needs zero changes. `MockGateway` implements the same HMAC-signature verification shape a real provider would use (sign `order_id|payment_id` with a shared secret) specifically so the verification code path in `PaymentService.Capture` is exercised realistically, not just stubbed to always-succeed.
- **COD orders never go through `/payments/initiate`.** Cash-on-delivery orders are created with `payment_status = pending` and are expected to be marked paid via a separate "mark COD collected" action once the Delivery module (Phase 5) exists and a delivery partner confirms cash collection. That action does not exist yet — `orders.payment_status` for COD orders will sit at `pending` indefinitely until Phase 5 adds it. Flagging so it isn't mistaken for a bug later.
- **Payment capture is the only code path allowed to mark an order `paid`**, and it always re-verifies the gateway signature server-side (`gateway.VerifyCallback`) before doing so — a client cannot simply POST "payment succeeded" and have it believed. Both the direct client-callback endpoint (`POST /payments/capture`) and the webhook endpoint (`POST /payments/webhook`) funnel through the same `PaymentService.Capture` method, so there's exactly one place this trust decision is made.
- **`PaymentService.Capture` is idempotent** (returns the existing transaction if already `captured`) since both a client-side callback and a gateway webhook commonly fire for the same successful payment — without idempotency this would double-process. It is NOT yet idempotent against concurrent calls (no row-level lock/`SELECT ... FOR UPDATE`), so a true race between the two arriving at the same instant could still double-call `orderPay.SetPaymentStatus` (harmless, since that's just an idempotent status set) — flagged as low-risk but not fully closed.
- **If `orderPay.SetPaymentStatus` fails after a successful gateway capture, `Capture` still returns success** rather than erroring — the money genuinely moved, so telling the client "payment failed" would be actively wrong. This creates a possible drift between `payment_transactions.status = captured` and `orders.payment_status != paid`. A reconciliation job to catch and repair this drift is a real Phase 4 gap, not built yet — flagged prominently since it's a correctness issue for money, not a cosmetic one.
- **The webhook endpoint (`POST /payments/webhook`) is unauthenticated by design** (gateways can't send a bearer token — they authenticate via their own signature scheme instead), but this codebase does NOT yet verify a gateway-level webhook signature header (e.g. Razorpay's `X-Razorpay-Signature`) before parsing the body — it currently relies entirely on `PaymentService.Capture`'s per-payment HMAC check. For a real gateway integration, add webhook-envelope signature verification as a first step in the handler, before any per-payment logic runs, so malformed/spoofed webhook bodies are rejected before touching application code.
- **Refunds are synchronous and gateway-initiated only** — there's no webhook handling for asynchronous refund completion (`refund.processed` events are explicitly ignored in the webhook handler, see comment there). Real gateways often process refunds asynchronously; if `gateway.Refund` returns success but the actual funds movement happens later, this module would show a refund as `completed` prematurely. Flagged as a simplification that needs revisiting once a real gateway is wired in.
- **Saved payment methods store only opaque gateway tokens** (`saved_payment_methods.gateway_token`), never raw card/UPI details — this keeps the platform out of PCI-DSS card-data scope, which matters a lot for a real launch and was treated as non-negotiable rather than a "revisit later" item.

## Phase 5 — Delivery

- **Dispatch is nearest-available-partner, single-candidate, no retry loop.** `DeliveryService.FindAndOffer` finds the single nearest verified/online/under-capacity partner within a flat search radius and offers them the delivery. If they reject (or the offer times out — no timeout mechanism exists yet), nothing automatically re-offers to the next-nearest candidate; the caller (restaurant/admin) has to call `FindAndOffer` again manually. A production dispatch system would need: an offer timeout with auto-expiry, batched/parallel offers to multiple candidates, re-offer-on-reject without a manual re-trigger, and probably ML-based ETA/routing rather than straight-line distance. This implementation is a correct but minimal starting point, not a competitive dispatch algorithm — flagging clearly so it isn't mistaken for more sophisticated than it is.
- **`MaxActiveDeliveries` is a single flat cap (3) for every partner**, regardless of vehicle type, distance already committed, or time of day. A bicycle courier and a car driver get the same concurrency limit. Revisit once there's real data on what partners can actually handle.
- **Partner location updates write directly to Postgres on every ping** (`UpdateDeliveryPartnerLocation`), with no rate limiting or Redis-backed live layer. If partner apps ping every few seconds, this is a lot of UPDATE traffic on a GEOGRAPHY-indexed column for a table that's also being queried for nearby-search — this will not scale past pilot volume. The intended production design (not built) is: partner app pings a Redis GEO set (sub-second writes, no disk I/O) for live map rendering, with periodic (e.g. every 30s–1min) snapshots persisted to Postgres for the `current_location` column used by nearest-partner search. Flagged as the single most likely performance bottleneck in this phase if usage grows.
- **Delivery confirmation uses a 4-digit OTP shown only to the customer** (`GET /delivery/orders/:orderId/code`, ownership-checked) and entered by the partner at drop-off (`POST /delivery/partner/assignments/:id/deliver`). This is deliberately never returned in any partner-facing or restaurant/admin-facing response — see the comment on `assignmentToJSON` — because a partner who could look up their own delivery code could self-confirm a delivery that never happened. This is the second time in this codebase an information-exposure mistake was caught and fixed during development rather than shipped (the first was the Orders ownership gap in Phase 3) — worth a second look at any new endpoint in future phases with the same question: "who should NOT be able to see this field?"
- **`MarkPickedUp`/`MarkDelivered` update Order status in the same call** (`out_for_delivery` / `delivered` respectively) via the `OrderStatusUpdater` interface, and if that secondary update fails, the assignment-side state change is still considered successful and returned to the caller — same "the real-world event already happened, don't lie about it" reasoning as Payment capture in Phase 4. This creates the same class of potential drift (assignment says `delivered`, order status lags) and needs the same reconciliation-job fix eventually — not built yet, same flag as Phase 4's payment/order drift.
- **No delivery partner rating/review flow yet** — `delivery_partners.rating_avg`/`rating_count` columns exist but nothing writes to them. That's a Ratings/Reviews module (not yet built, part of the remaining roadmap) that will need to update this table once it exists.
- **Assignment cancellation (`POST /delivery/assignments/:id/cancel`) does not cascade to re-dispatch.** Cancelling an assignment (e.g. partner unreachable) releases their capacity slot but does not automatically call `FindAndOffer` again for the order — a human (restaurant/admin) has to notice and re-trigger dispatch. Same manual-retry gap as the rejection flow above.

## Phase 6 — Notifications

- **`Notify` is synchronous, best-effort, and never propagates a send failure back to the caller** — same reasoning as everywhere else in this codebase where a secondary side-effect follows a real event that already happened (order status changes, payment capture, delivery pickup): a failed push notification must not make `OrderService.UpdateStatus` or `PaymentService.Capture` appear to fail. This is now a recurring pattern across four modules (Orders, Payments, Delivery, Notifications itself for its own channel sends) and is documented once here rather than re-litigated per module.
- **No outbox/background worker — sends happen inline in the request path.** `NotificationService.Notify` writes a `notifications` row and immediately attempts to send via the relevant channel sender, all within the HTTP request that triggered it (e.g. a customer's `PATCH /restaurants/:id/orders/:id/status` call). This means a slow or down push/SMS/email provider directly slows down or degrades unrelated API calls. The correct production design is an outbox table (already effectively what `notifications.send_status = 'pending'` rows are) plus a background worker that picks up pending rows and sends them independently of the request that created them, with retries and backoff. Not built yet — this is the single biggest structural gap in this phase, flagged clearly rather than glossed over.
- **Default channel-per-category mapping is a product policy decision baked into code** (`defaultChannels` in `notification_service.go`), not sourced from any spec — e.g. promotional notifications never default to SMS/email to avoid spam complaints, order cancellation adds SMS on top of push+in-app since it's higher-stakes. These defaults are reasonable guesses, not confirmed requirements — flagging so they're easy to find and revisit rather than buried in a long switch statement.
- **User preferences are opt-out only, "enabled by default."** Absence of a `notification_preferences` row means enabled; a row only ever exists to record an explicit override. This means a newly-added category is automatically on for all existing users with no migration needed — a deliberate choice, but also means there's no way to build a "let users opt in to new categories" flow later without changing this default-on assumption.
- **Cross-module wiring**: Orders, Payments, and Delivery each take an optional `Notifier` interface (nil-safe — every call site checks before using) rather than a hard dependency on the Notifications module, so those modules still compile and function with notifications entirely absent (e.g. in tests). The actual trigger points chosen: Orders fires on placement, every customer-visible status transition, and cancellation; Payments fires on capture, capture-verification-failure, and refund completion; Delivery fires on partner acceptance (not on 'offered', since an offer can still be rejected — "someone is bringing your food" only becomes true once accepted). This set of trigger points is a reasonable first pass, not exhaustively validated against a product spec — e.g. there's no "your delivery partner is 5 minutes away" proximity-based notification yet (would need the Redis-backed live-location layer flagged as missing in Phase 5's assumptions first).
- **`DeviceLookupAdapter`/`ContactLookupAdapter` read the `devices`/`users` tables directly** via the shared sqlc `Queries` struct rather than going through Identity/Users' application services — see the doc comment on `lookup_adapters.go` for why this is a deliberate, narrow exception to the "define an interface, implement it via the owning module's service" pattern used everywhere else.

## Phase 7 — Settlements

- **Payouts are manually confirmed, not gateway-automated.** Unlike Payments (Phase 4), which has a real `domain.PaymentGateway` abstraction for charging customers, Settlements has no equivalent payout-gateway abstraction — `PayRestaurantSettlement`/`PayDeliverySettlement` just record that a payout reference exists (presumably from a manual bank transfer or a payout done through a separate admin tool), they don't call out to any provider. A real implementation would want the same abstraction treatment (a `PayoutGateway` interface wrapping Razorpay X / Stripe Connect / similar) — deliberately not built here to avoid a second half-finished gateway integration; flagged as the natural next step once one gateway relationship (customer-charging) is proven out.
- **`ProcessCycle` is safely re-runnable only BEFORE any payouts in that cycle are marked paid.** ~~Because `UpsertRestaurantSettlement`/`UpsertDeliverySettlement` use `ON CONFLICT ... DO UPDATE`, re-processing a cycle recomputes and overwrites `net_payable` even on rows already marked `paid`...~~ **FIXED in the Testing/Hardening pass**: `ProcessCycle` now calls `cycleHasAnyPaidSettlements` before doing any work and rejects with a conflict error if any restaurant or delivery settlement in the cycle is already `paid`, regardless of the cycle's own status (this catches not just a cleanly-`completed` cycle being re-run, but also a cycle stuck in `processing` after a crash where some settlements were already paid out before the crash). See `internal/modules/settlements/application/settlement_service.go`.
- **Restaurant commission is calculated at settlement time, using the restaurant's CURRENT `commission_pct`**, not whatever it was when each individual order was placed. If a restaurant's commission rate changes mid-cycle, every order in that cycle is settled at the new rate, not a blended rate. For most cases (rate changes are infrequent, cycles are short) this is a reasonable simplification, but it's an assumption worth confirming against actual business rules before relying on it — a real implementation might need to snapshot `commission_pct` onto the order at placement time instead (the same "snapshot at the moment of commitment" principle already used for order pricing in Phase 3).
- **Delivery partner pay is a flat per-delivery fee** (₹30, hardcoded in `main.go`'s `PayoutConfig`), with no distance-based, time-based, or surge component, and no incentive/bonus scheme (`incentive_amount` always 0). Matches the same "deliberately simple placeholder, not real pricing logic" caveat already flagged for order tax/delivery-fee pricing in Phase 3 — this is the delivery-partner-earnings equivalent of that gap.
- **Payout account tokenization is a placeholder, not a real integration.** `RegisterPayoutAccount` currently stores the raw account number as the `account_token` field (with a NOTE comment flagging this explicitly in the code) rather than exchanging it with a real payout provider for an opaque token. This does NOT meet the same data-minimization bar as `saved_payment_methods` in Payments and needs fixing (encrypt at rest at minimum, tokenize via a real provider ideally) before this table holds real bank details — called out clearly rather than left as a subtle gap, since it's the one place in this phase that's worse than its Phase 4 counterpart rather than equivalent to it.
- **`ListMyDeliverySettlements`/payout account registration resolve the caller's partner ID from their authenticated user ID** (via a `PartnerLookup` interface, implemented by `DeliveryService.GetPartnerIDForUser`) rather than trusting a client-supplied `partner_id`. An earlier draft of this handler took `partner_id` as a request field, which would have let any authenticated delivery partner view or modify another partner's settlement/payout data by supplying a different ID — caught and fixed before shipping. This is the third time in this codebase an ownership-exposure bug was caught during development rather than shipped (after the Phase 3 order-ownership gap and the Phase 5 delivery-OTP exposure) — worth continuing to ask "who should NOT be able to see/act on this?" for every new endpoint in future phases.

## Phase 8 — Admin RBAC

- **This module adds a finer-grained permission layer ON TOP OF, not instead of, the coarse `RequireRole("admin")` check used everywhere since Phase 2.** Every existing admin route still works exactly as before (any user with `primary_role = 'admin'` can hit it) — `middleware.RequirePermission` exists and is proven out on this module's OWN routes (`admin.manage_roles`, `admin.assign_roles`), but was NOT retrofitted onto any of the ~15 pre-existing admin endpoints from earlier phases (restaurant approval, KYC review, refunds, settlement payouts, etc.) — those all still rely solely on the coarse admin-role check. This is a real, intentional scope boundary, not an oversight — flagged clearly so "Admin RBAC exists" isn't mistaken for "every admin action is now permission-gated."
- **Audit logging (separately from permission-gating) WAS retrofitted onto three specific pre-existing actions**: restaurant approval/rejection, payment refunds, and settlement payouts — chosen as the highest-stakes/most financially consequential actions in the platform. These three now write an `admin_audit_log` row when performed, in addition to still being gated by the coarse `RequireRole("admin")` check (not `RequirePermission`). Every other admin/state-changing action (order status updates, delivery KYC reviews, user suspension, menu edits by staff, etc.) does neither — no audit log, no fine-grained gate.
- **`HasPermission` queries the database on every permission-gated request** rather than caching permissions in the JWT or in Redis. This is a deliberate correctness-over-latency tradeoff (a revoked permission takes effect immediately, not after the admin's access token expires) but will add a real per-request cost if permission-gated routes see heavy traffic — a Redis-backed permission cache with short TTL (invalidated on grant/revoke) would be the natural fix if this becomes a bottleneck, not built here.
- **`SetRolePermissions` (delete-all-then-insert-each) is not wrapped in a DB transaction**, same class of gap as `orders.Create` back in Phase 3 — a failure partway through could leave a role with a partial permission set. Flagged explicitly in the repository code comment rather than repeating the pattern silently.
- **Only one role is seeded** (`super_admin`, with every permission) — the migration deliberately does NOT seed `finance_admin`, `support_agent`, or other narrower roles, since which specific permissions belong to which named role is a business/org-structure decision this codebase shouldn't guess at. An operator is expected to create those roles via the API (`POST /admin/rbac/roles` + `PUT /admin/rbac/roles/:id/permissions`) once real org structure is known.
- **No UI/API for bulk-migrating existing `primary_role='admin'` users into the new RBAC system** — an existing admin user has no admin_roles/permissions rows unless someone explicitly grants them via `POST /admin/rbac/users/:userId/roles/:roleId`. Since the coarse `RequireRole("admin")` check still governs most routes (see above), this doesn't break anything today, but the three retrofitted fine-grained routes (via `RequirePermission`) would reject an admin who hasn't been granted the relevant role — worth a one-time migration script granting `super_admin` to all existing `primary_role='admin'` users before relying on the fine-grained checks in practice.

## Phase 9 — Search

- **Postgres full-text search (tsvector + GIN), not a dedicated search engine.** Deliberately avoids adding Elasticsearch/Meilisearch/Typesense as a second datastore + sync pipeline for something Postgres FTS can handle at this platform's likely scale. `websearch_to_tsquery` gives reasonably forgiving query parsing (handles quoted phrases, `-exclusion`, implicit AND) without the platform needing its own query-syntax layer. Revisit if relevance quality (no typo-tolerance/fuzzy matching — "biryani" won't match "biriyani") or query volume outgrows what a GIN index serves well; that's the natural trigger for introducing a real search engine, not a decision to make preemptively.
- **This module is a second deliberate exception to the "read through a narrow consumer-defined interface" pattern**, reading the `restaurants` and `menu_items` tables directly (see the migration's header comment) — same class of exception as Notifications' `DeviceLookupAdapter`/`ContactLookupAdapter` in Phase 6. Full-text ranking combined with geo-filtering and joins is inherently a SQL-level concern that doesn't decompose into per-record interface calls without losing the ability to let Postgres do the ranking/filtering/sorting in one query.
- **Search relevance ranking (`ts_rank_cd`) and geo-distance are combined by sorting rank first, distance second** (`ORDER BY rank DESC, distance_km ASC`) rather than a blended score. This means a strong text match 8km away always outranks a weak text match 1km away. Whether that's the right tradeoff for a food-delivery search experience (where "close and available now" often matters more than exact text relevance) is a product decision, not something this implementation validated — flagged as worth A/B testing or at minimum a deliberate product call, not just accepting the naive ordering.
- **No typo tolerance, synonym expansion, or stemming beyond English's built-in Postgres text search dictionary** (which does handle basic stemming — "burgers" matches "burger" — but nothing beyond that). "Chiken" won't match "chicken." A trigram index (`pg_trgm`) layered on top would get typo-tolerance without a full search-engine migration — a reasonable next increment if this proves to matter, not built here.
- **Search query logging happens on every search, unconditionally** (including from search-engine crawlers or automated/abusive traffic if any reaches these public endpoints) — there's no rate limiting specific to search beyond the platform-wide global rate limiter already in `middleware.RateLimit`, and no bot/crawler filtering. If `search_logs` needs to stay a clean signal for trending-searches/analytics, this is worth revisiting once real traffic patterns are known.
- **`OptionalAuth` middleware (new in this phase) silently proceeds unauthenticated on ANY token problem** — expired, malformed, wrong signature, all treated identically to "no token provided." This is correct behavior for its one current use case (Search, where the whole point is working for browsing customers) but means a route mounting `OptionalAuth` can never distinguish "not logged in" from "tried to log in with a bad token" — fine for Search, but a future consumer of this middleware should confirm that ambiguity doesn't matter for their use case before reusing it.
- **No search index staleness concern** — because `search_vector` is a Postgres `GENERATED ALWAYS AS ... STORED` column, it updates synchronously and transactionally with every `restaurants`/`menu_items` write, so there's no separate reindexing step and no window where search results can lag behind the actual data (unlike a typical external-search-engine setup, which usually has async indexing lag). This is one of the genuine advantages of the Postgres-FTS choice over a separate search engine, worth noting since most of this document flags gaps rather than deliberate wins.
